# devlog

开发日志（devlog）是**按天追加的历史账**，回答"一路都发生了什么"。它和另两层分工清晰，互不重复：

| | 答什么 | 自动读？ |
|---|---|---|
| HANDOFF.md | 当下态：现在在哪、下一步 | 每次会话开始读 |
| PLAN.md | 任务级：做到什么程度算完 | 有则读 |
| **devlog/** | **历史：曾经发生了什么** | **平时不读，按天按需读** |

> 名字提示：这是**开发过程**日志，与脚手架将来跑业务工作流时产出的"工作日志"（业务产物）刻意区分——别混。

## 平时不读（关键）

devlog **不进常驻上下文**——会话开始不读它，CLAUDE.md 也不引用它。只有用户明确说"看某天的日志"时，才去读**那一天**那一篇，不全量、不自动。这是它不拖累上下文的前提。

## 怎么写

- **位置与命名**：`devlog/<YYYY-MM-DD>.md`，一天一个文件（如 `devlog/2026-06-22.md`）。文件夹不存在则创建。
- **一天一文件**：同一天多次会话**追加到当天那篇**，不要一会话开一个新文件（否则又碎成流水账）。
- **时机**：通常在 `/done` 收尾时顺手写当天这篇（done skill 会调用本流程）。
- **模板**：见 `templates/devlog-day.md`。

## 记什么（纪律：只记 git 记不下的）

git 已经逐文件记录了"改了什么"，devlog **不要重复**逐文件列改动。它记的是 git 看不出的东西：

- **做了什么**：这天的主线，一两句话，不是文件清单。
- **关键决策**：选了 X 弃了 Y，因为 Z——日后最值得回看的"为什么"。
- **踩坑/死路**：试过不通的路，省得以后重蹈。
- **下一步**：收尾时的待办（与 HANDOFF.md 的"下一步"呼应，不冲突）。

## 怎么读

用户指定某天（如"看 2026-06-22 的日志"或 `/devlog 2026-06-22`）→ 只读 `devlog/<那一天>.md`。没指定日期时可列出 `devlog/` 下有哪些天，让用户挑。

## 硬约束

- 单篇日志聚焦当天，**不堆历史**——历史靠"多篇按天的文件"承载，不是单篇越写越长。
- 不逐文件列改动（git 的活）；不写"当前态/下一步动作"以外重复 HANDOFF.md 的内容。
- 平时绝不自动读，避免重新变成上下文负担。
