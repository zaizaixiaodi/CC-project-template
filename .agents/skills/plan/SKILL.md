# plan

PLAN.md 是**任务协议**：开工前把目标、边界、验收标准写死，防止"看起来做完了"的静默失败。它管一次任务的"做什么、做到什么程度"；session 之间的接力由 HANDOFF.md 管。

## 何时创建
用户调用 `$plan` 时直接从 [模板](templates/PLAN.md) 创建。
复杂且需要多轮验收的已授权任务可自行维护计划；仅缺少会影响范围或验收的信息时询问。
简单任务不创建。已有 PLAN.md 先读取并更新，不覆盖其他在途任务。
创建目标、边界、步骤、可验证验收标准及验证手段；不要以创建计划为额外审批门槛。

## 与 HANDOFF.md 的分工

| | PLAN.md | HANDOFF.md |
|---|---|---|
| 粒度 | 任务级 | session 级 |
| 管什么 | 目标、边界、验收标准、步骤进度 | 在途状态、下一步动作、决策、踩坑 |
| 进度勾在哪 | 实施步骤的 checkbox | 不勾，计划段只留一行指针 |

PLAN.md 存在时，HANDOFF.md 的"计划 (Plan)"段**只写一行**：`见 PLAN.md（当前在第 N 步）`，不要两处维护。

## 变更纪律（核心）

计划在开发中变更是常态，按性质分两级处理：

- **方向性变更**（目标、不做什么、验收标准变了）：直接把 PLAN.md **改到新状态**，同时在 HANDOFF.md 的"在途决策"记一行——`计划变更：改 X 弃 Y，因为 Z`。来龙去脉就靠这一行 + git 历史，**不另设 devlog**。
- **细节性变更**（步骤拆分调整、补充验证项）：直接改，不留痕。git 兜底。

## 完成归档

验收标准全部达成后：

1. 有沉淀价值的内容先迁出：可复用的验证清单/踩坑 → 按 handoff skill 的冲刷规则分流（AGENTS.md / docs / 专属 skill）。
2. 把 PLAN.md 移动到 `archive/plans/<YYYY-MM-DD>-<任务名>.md`（目录不存在则创建）。
3. 更新 HANDOFF.md：计划段的指针行删除或换成下一任务。

## 硬约束

- PLAN.md ≤ **100 行**；根目录同时只允许**一个**活跃 PLAN.md。
- 验收标准每条必须**5 秒内可判断是否达成**（"条款逐条核对完毕"✓，"质量要高"✗）。
- 验证手段不限于命令：核对清单、交叉比对、人工确认项都算，但必须写明**具体怎么查**。
